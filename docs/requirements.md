# Deep Research —— 需求与技术选型文档

> 版本：v0.1（草案）
> 目标岗位：AI 应用开发 / Agent 开发（偏后端 + 全栈）
> 项目定位：一个多智能体深度研究流水线，输入一个问题，自动完成「拆解 → 检索 → 写作 → 审核」，输出带引用来源的调研报告。

---

## 1. 项目概述

### 1.1 一句话定位

一个多智能体深度研究系统：用户提出一个问题，系统自动拆解子任务、并行搜索与抓取资料、通过 RAG 检索并溯源，最后由多个 Agent 协作产出一份**带引用来源、可追溯**的调研报告。

### 1.2 项目目标

1. **展示 Agent 开发核心能力**：工具调用循环、规划、多智能体编排、RAG、结构化输出。
2. **展示后端工程能力**：流式输出、长任务队列、断点恢复、可观测性、成本控制、评估（eval）。
3. **产出可演示成果**：一个能现场点开的 Web 界面，输入问题即可看到完整研究过程。

### 1.3 目标用户与使用场景

- 需要快速了解一个陌生领域的人（投资人、产品经理、学生）。
- 需要「多来源交叉验证 + 引用溯源」的调研场景（竞品分析、技术选型调研、行业报告）。

### 1.4 范围界定（做什么 / 不做什么）

**做**：任务拆解、搜索/抓取、RAG 检索与引用、多智能体协作、流式输出、eval、部署。

**不做（本期）**：多租户、付费/计费、复杂的权限体系、网页登录鉴权（本地 demo 即可）、自训练模型。

## 2. 功能需求

优先级说明：**P0 = MVP 必须**，**P1 = 核心完整版**，**P2 = 工程化加分项**。

### 2.1 功能清单

| 优先级 | 模块 | 需求描述 | 验收标准 |
|---|---|---|---|
| P0 | 任务入口 | 用户提交一个研究问题 | 创建任务并进入处理流程 |
| P0 | Agent 核心循环 | 单 Agent + 工具调用循环（搜索、抓取） | 能完成「问 → 查 → 写」闭环 |
| P0 | 流式输出 | 通过 SSE 实时推送进度与中间结果 | 前端实时看到「正在搜索 / 正在写作」 |
| P0 | 报告产出 | 输出 Markdown 报告，含来源链接 | 报告可读、有出处 |
| P1 | 任务规划 | Planner 把大问题拆成 N 个子问题 | 拆解合理、子任务可并行 |
| P1 | 多智能体 | Researcher / Writer / Critic 分工协作 | 各角色职责清晰、可独立配置 |
| P1 | RAG 检索 | 抓取内容向量化入库，写作时检索并溯源 | 每个结论能标注来源 |
| P1 | 引用审核 | Critic 校验引用是否真实、质量是否达标 | 不合格时触发补充检索 |
| P2 | 任务队列 | 长任务放队列异步执行 | 不阻塞请求、可并发 |
| P2 | 断点恢复 | 任务状态持久化，失败/中断后可续跑 | 重启后能从断点继续 |
| P2 | 取消/超时/重试 | 单次工具调用有超时与重试，任务可取消 | 异常可恢复、不卡死 |
| P2 | eval 评估集 | 黄金问题集 + LLM-as-judge 评分 | 迭代时可量化回归 |
| P2 | 可观测性 | 每步 trace、token 用量、成本统计 | 能定位哪一步慢/贵 |
| P2 | 前端界面 | 进度树 + 报告展示 + 引用跳转 | 完整可演示 |
| P2 | 部署 | Docker Compose 一键启动 | `docker compose up` 即可运行 |

### 2.2 非功能需求

| 类别 | 需求 |
|---|---|
| 性能 | 流式首 token 延迟 < 3s（本地）；完整报告视任务复杂度 1–5 分钟 |
| 可靠性 | 工具调用超时（默认 30s）+ 重试（默认 2 次）；任务可取消 |
| 成本 | 分模型分层（规划用强模型、摘要用便宜模型）；单任务 token 预算上限 |
| 可观测性 | 全链路 trace；每个工具的输入/输出/token/耗时可查 |
| 安全 | API key 不落前端；抓取目标限速；**防 SSRF**（抓取时禁内网地址） |
| 可扩展性 | 工具、Agent 角色、模型 Provider 均可插拔 |

## 3. 系统架构

```
                    ┌────────────────────────────┐
                    │        前端 (Next.js)        │
                    │  输入框 / 进度树 / 报告展示   │
                    └─────────────┬──────────────┘
                                  │ REST + SSE
                    ┌─────────────▼──────────────┐
                    │        API 层 (FastAPI)     │
                    │  创建任务 / 查询状态 / 流式    │
                    └─────────────┬──────────────┘
                                  │
                    ┌─────────────▼──────────────┐
                    │        编排器 (Orchestrator) │
                    │   Planner → 并行 Researcher  │
                    │   → Writer → Critic 循环     │
                    └───┬─────────┬──────────┬────┘
                        │         │          │
              ┌─────────▼───┐ ┌───▼────────┐ ┌▼─────────────┐
              │  工具层       │ │  RAG 模块   │ │  Provider 层  │
              │ 搜索/抓取/检索│ │ 切分/向量/检│ │ LLM/Embedding│
              └─────────┬───┘ └───┬────────┘ └───┬─────────┘
                        │         │              │
              ┌─────────▼─────────▼──────────────▼─────────┐
              │  基础设施：PostgreSQL(pgvector) + Redis + 外部API │
              └─────────────────────────────────────────────┘
```

### 3.1 模块职责

| 模块 | 职责 |
|---|---|
| API 层 | 任务 CRUD、SSE 流式、鉴权（本地可选） |
| 编排器 | Agent 状态机：拆解 → 并行研究 → 写作 → 审核循环 |
| 工具层 | 可插拔工具抽象：`search` / `fetch` / `vector_search` |
| RAG 模块 | 切分、向量化、检索、重排 |
| Provider 层 | LLM 与 Embedding 的统一抽象，支持多厂商/多模型路由 |
| 状态存储 | 任务、子任务、来源文档、trace 事件 |

## 4. 技术选型

### 4.1 总览

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.12 | AI 生态最全，简历通用 |
| 后端框架 | FastAPI | 原生 async + SSE，Swagger 自动文档 |
| Agent 编排 | 先手写循环 → 再迁移 LangGraph | 先懂原理，再懂框架 |
| LLM | Provider 抽象 + 多模型路由 | 强模型规划 / 便宜模型摘要 |
| 搜索 | Tavily（默认）/ Brave Search | 专为 LLM 设计，有免费额度 |
| 抓取 | httpx + trafilatura | 轻量、正文提取好 |
| Embedding | BGE（本地，默认）/ OpenAI / 阿里 | 本地免费，可切换 |
| 向量库 | pgvector（MVP）→ Qdrant（进阶） | 复用 Postgres，少一个服务 |
| 关系存储 | PostgreSQL 16 | 任务/文档/事件 |
| 队列/缓存 | Redis + ARQ（进阶） | MVP 用 async 即可 |
| 前端 | Next.js + React + Tailwind | 全栈统一，SSE 流式 |
| 可观测性 | 结构化日志 + Langfuse（进阶） | trace + 成本 |
| 部署 | Docker Compose + Caddy | 一键启动，放 demo 链接 |
| 测试 | pytest + eval 评估集 | 单元 + 回归 |

### 4.2 关键决策与理由

#### ① LLM 选型（最重要的决策）

设计原则：**用 Provider 抽象层解耦**，所有调用走统一接口，切换厂商只改配置不改代码。

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Claude（Opus/Sonnet） | 工具调用稳、长上下文强、写报告质量高 | 有成本 | 主模型首选 |
| GPT-4o 系列 | 生态成熟、速度快 | 有成本 | 备选 |
| DeepSeek / Qwen（国内） | 便宜、可直连、中文好 | 工具调用稳定性略弱 | 摘要/降级模型，控成本 |

**推荐策略**：规划与写作用强模型，抓取摘要用便宜模型（成本分层）。这是简历上「成本控制」的卖点。

#### ② Agent 编排：手写 vs 框架

| 方案 | 优点 | 缺点 |
|---|---|---|
| 手写 tool-calling 循环 | 彻底理解 agent 原理，面试能讲透，无依赖 | 工作量略大 |
| 直接用 LangGraph | 快、生态好、简历能写「用过框架」 | 面试深问原理可能答不深 |

**推荐**：先手写核心循环（工具抽象 → 模型决策 → 执行 → 观察 → 再决策），跑通后再把循环迁移到 LangGraph。既能讲原理，又能写「熟悉 LangGraph」。

#### ③ 搜索 API

| 方案 | 免费额度 | 特点 |
|---|---|---|
| Tavily | 有（每月 1000 次左右） | 专为 LLM 设计，返回已清洗的正文+相关度 |
| Brave Search | 有（每月 ~2000 次） | 传统搜索，返回原始结果 |
| SerpAPI | 付费 | Google 结果，稳定但贵 |

**推荐 Tavily** 作为默认，工具层抽象成接口，方便换。

#### ④ Embedding + 向量库

| 方案 | 优点 | 缺点 |
|---|---|---|
| BGE（sentence-transformers 本地跑） | 免费、离线、中文好 | 首次需下载模型 |
| OpenAI text-embedding-3-small | 简单、质量好 | 有成本、需联网 |
| 阿里 text-embedding-v3 | 便宜、中文好 | 需阿里云 key |

向量库：**MVP 用 pgvector**（复用 Postgres，简历还能写「用 Postgres 做向量检索」）；进阶换 **Qdrant**（更好的过滤与重排）。

#### ⑤ 前端

- **MVP**：Vite + React 单页（快、够用）。
- **进阶/完整版**：Next.js，SSE 流式展示进度树，含报告渲染与引用跳转。

#### ⑥ 队列与异步

- **MVP**：FastAPI 原生 async + BackgroundTasks，够跑单机 demo。
- **进阶**：Redis + ARQ（或 Celery），支持真正并发的多任务、断点恢复。

#### ⑦ RAG 知识组织：任务隔离 vs 全局知识池 vs 分层

三种方案对比：

| 方案 | 串题风险 | 跨任务复用 | 可清理/统计 | 复杂度 | 大数据量表现 |
|---|---|---|---|---|---|
| A 全局知识池 | 高 | 强 | 差 | 低 | 检索随总量退化、无法清理 |
| B 纯任务隔离 | 无 | 无 | 好 | 低 | 稳定，但重复提问零复用、最费时 |
| C 隔离 + 长期库 | 低 | 有（受控） | 好 | 中 | 可持续：范围小、长期库可限流淘汰 |

**选 C。** 核心设计：

- **任务库**：每次研究一个 `research_task`，抓取来源通过关联表限定「本任务检索范围」；引用编号用任务内局部编号（每份报告从 `[1]` 开始）。
- **长期库**：来源满足打分阈值后晋升，可设上限与淘汰，支持跨任务复用。
- **检索**：默认只搜本任务，命中不足时回退长期库（双阶段）。

**数据晋升到长期库的判定**（打分制）：

```
晋升分 = 复用次数×2 + 被引用进报告×1 + 权威域名(+2)/低质域名(−2) + 正文质量(+1) − 易过期内容(−3)
晋升分 ≥ 阈值 → 晋升长期库（带 last_referenced_at / expires_at，用于淘汰）
```

**耗时与规模**：三方案在「向量检索本身」上几乎无差别（HNSW 毫秒级）；真正耗时大头是抓取 + LLM 调用。C 通过「复用 + 不串题」在重复提问和大数据量下最优。实现上避免「一张大表 + WHERE 过滤」的 filtered-HNSW 性能退化，把任务库与长期库物理分层（进阶可迁 Qdrant）。

## 5. 数据模型（草案）

| 表/集合 | 字段 | 说明 |
|---|---|---|
| `research_task` | id, question, status, created_at, updated_at | 顶层任务 |
| `subtask` | id, task_id, question, status | Planner 拆解的子问题 |
| `source` | id, url(唯一), title | 来源（全局去重，只存一份） |
| `chunk` | id, source_id, chunk, embedding | 分块 + 向量（归 source，不重复） |
| `task_source` | task_id, source_id, citation_no | 本任务引用编号（任务内从 1 起） |
| `source_pool` | source_id, is_long_term, quality_score, last_referenced_at, expires_at | 长期库（晋升/淘汰） |
| `report` | id, task_id, markdown, citations | 最终报告 |
| `trace_event` | id, task_id, step, tool, input, output, tokens, cost, duration_ms | 可观测性 |

## 7. 风险与权衡

| 风险 | 应对 |
|---|---|
| 抓取内容质量差 / 被反爬 | 用搜索 API 返回的正文为主，抓取做降级；加超时与重试 |
| 引用「幻觉」（引用不存在的来源） | Critic 审核 + 引用必须来自已入库文档 |
| token 成本失控 | 模型分层 + 单任务预算上限 + trace 统计 |
| 长任务阻塞/崩溃 | 状态持久化 + 断点恢复 + 队列 |
| SSRF 安全风险 | 抓取前校验 URL，禁用内网/本地地址 |
